# LLM Engineering: From Architecture to Edge — Project Write-Up

**Author:** Rahul
**Repo:** `llm-engineering-architecture-to-edge` (this repository)
**Status at time of writing:** in progress, 8 of 24 planned work-items complete, remaining items code-complete and waiting on GPU runs / deployment (see `specs/STATUS.md` for the live table)

This document is the full story of the project — why I started it, how I planned it, how I built each piece, how I tested it, what went wrong along the way, and where it stands today. I'm writing it because I'm putting this on my resume, and I want a record that goes deeper than the bullet points: not just "fine-tuned an LLM" but the actual decisions and trade-offs behind that sentence.

---

## 1. Why I built this

I wanted one project that could answer three separate interview questions I kept getting asked in different words:

1. "Do you actually understand how a transformer works, or have you only ever called `.fit()` on someone else's model?"
2. "Have you fine-tuned a model on a real task, and can you prove it's actually better than just prompting a bigger one?"
3. "Have you ever *operated* a model — served it, monitored it, deployed it — or only trained one and stopped?"

Most portfolio projects answer one of these. I wanted a single repo that answers all three honestly, with numbers, not adjectives. That became the three-chapter structure:

- **Chapter 1 — Architecture.** A GPT-style language model written from scratch in pure PyTorch — no `transformers`, no `nn.Transformer`, no borrowed attention implementation. If I can't write attention by hand, I don't understand it.
- **Chapter 2 — Adaptation.** A QLoRA fine-tune of a real small open model (`Qwen2.5-Coder-1.5B-Instruct`) turned into a Java/Spring code reviewer that emits structured JSON, benchmarked head-to-head against the base model and against just prompting a frontier API.
- **Chapter 3 — Operation.** That fine-tuned model quantized to GGUF, served behind FastAPI with schema validation and monitoring, containerized, and deployed to a free CPU host.

The three chapters deliberately don't share a model. Chapter 1 is a toy — it exists to prove mechanics, not to be good. Chapters 2 and 3 take a real model to production. Keeping those separate was a conscious choice: bolting "and it's also fast on CPU" onto a hand-rolled toy model would have been a much weaker story than showing the same reasoning applied twice, once for understanding and once for production.

**Constraints I set for myself up front**, because a project with no constraints doesn't prove anything about working under real ones:
- Solo, evenings/weekends, spread over roughly six months.
- A hard budget of about $1 in LLM API spend for the whole project (synthetic data generation + the frontier baseline).
- Free-tier GPU only for training (Colab/Kaggle) — no paid compute.
- CPU-only at serving time, on a free hosting tier — no GPU in production.

I think the budget constraint is actually the more interesting part of the story. Anyone can get a good result with unlimited compute. Getting a *defensible* result inside $1 and a free GPU tier is closer to what actually happens at a startup with no infra budget.

## 2. How I planned it

### 2.1 Starting point: one design document

I didn't start writing code. I started by writing `llm-engineering-architecture-to-edge.md`, a single design document at the repo root, before there was a repo. It locked down the decisions that everything downstream would depend on, so I wouldn't be re-litigating them three weeks in:

- Repo shape: one monorepo, three independent packages, shared `eval/` for the scoring logic they'd both need.
- The Chapter 2 task: Java/Spring code review emitting structured JSON (`severity`, `category`, `line`, `issue`, `suggested_fix`) — narrow enough to grade objectively, general enough to be a real skill.
- The data strategy: synthetic training data generated by a frontier model, honestly framed as *distillation* (a small model learning from a bigger one's outputs), with an **evaluation set that is independent of training and partly real** — mined from actual Java/Spring code, not just more synthetic examples — so the headline comparison isn't circular.
- The base model: `Qwen2.5-Coder-1.5B-Instruct`, chosen because it has the most mature QLoRA tooling at a size that fits on a free-tier GPU.
- The edge target: quantized GGUF via llama.cpp, served on a CPU-only free host.
- The hard operating rule: every entrypoint must run end-to-end on a tiny CPU "smoke" config in seconds. Full training and fine-tuning runs are launched by hand on a GPU box, never inside a normal working session. This is the rule that keeps a laptop-driven session from accidentally burning through free-tier GPU hours or shipping an unreproducible run.

From that one document I expanded five more planning documents (`planning/01-requirements.md` through `planning/05-api-design.md`) — functional and non-functional requirements, the module-level architecture, the system design, the database/schema decisions for the eval harness, and the API contract for the serving layer. All of that was locked *before* any code existed.

### 2.2 Turning the plan into a backlog

Design documents rot if nothing forces you to keep them honest against the code. So I broke the whole project into 24 discrete, independently-committable work items and tracked them in a single live status table (`specs/STATUS.md`), grouped into five tracks:

| Track | What it covers |
|---|---|
| **F** (Foundation) | repo scaffolding, the shared config convention, the eval harness and JSON schema — everything else depends on this |
| **C** (Chapter 2 / Adaptation) | task schema, the independent eval set, synthetic training data, the QLoRA fine-tune, the head-to-head eval table |
| **O** (Chapter 3 / Operation) | serving thin-slice, GGUF export, FastAPI guardrails, monitoring, containerizing, deploying |
| **A** (Chapter 1 / Architecture) | tokenizer, core transformer modules, training loop, KV-cache, quantization |
| **X** (cross-cutting) | README/architecture diagram, reproducibility, and interview-defense write-ups |

Each item got its own spec file: problem statement, scope, and — the part I actually cared about — acceptance criteria that are *mechanically checkable*. "The tokenizer works correctly" is not a criterion I'd accept from myself; "`decode(encode(t)) == t` for every string in the test corpus" is, because it's a thing a test can assert instead of a thing I can talk myself into believing.

The critical path is **F → C → O**: foundation, then the fine-tune, then serving it. Chapter 1 is intentionally a parallel track with nothing on the critical path depending on it, which is why its specs are numbered *after* Chapter 3's in the backlog even though "Chapter 1" reads first in the README — the reading order and the build order aren't the same thing, and I keep those separate on purpose.

### 2.3 Guardrails instead of good intentions

A few of this project's rules are the kind that are easy to break in the moment because breaking them feels locally reasonable — starting a full training run "just to see," reading the held-out evaluation set while debugging why a model is failing on it, committing a checkpoint because it's the artifact you just spent an hour producing. Those are exactly the mistakes that invalidate a result *and* are the easiest to talk yourself into. So instead of relying on remembering not to do them, I wrote small guard scripts that run before risky commands (a full-run pattern, a write to the frozen holdout directory, a commit that includes a weight file) and refuse them outright. A rule I have to remember every time is a rule I'll eventually forget once, at exactly the wrong moment. A guard that runs automatically doesn't have that failure mode.

## 3. How I built it — chapter by chapter

### 3.1 Foundation first

Before any model code, I built the pieces every chapter would need:

- **`pyproject.toml`** on `uv`, Python pinned to 3.12. The base install is deliberately tiny — just `pyyaml` and `jsonschema` — with the heavy stacks (`torch`, `transformers`/`peft`/`trl`, `llama-cpp-python`/`fastapi`) as opt-in extras per chapter. That means CI and the shared eval tests run in seconds without ever installing PyTorch.
- **A shared config loader** (`eval/config.py`) that reads YAML into a frozen dataclass and raises on a missing key *or* an unrecognized one. I made typos fail loudly on purpose: a Python-side default that silently fills in for a missing YAML key is a hyperparameter nobody can see in the config file, and a typo'd key is a setting I believe I set but didn't. Both produce a run that can't actually be reproduced from the config that supposedly describes it.
- **`eval/schema.json`** — the JSON-Schema contract every Chapter 2/3 model output has to satisfy — and **`eval/harness.py`**, which scores a batch of model outputs against it and reports schema-validity rate, "bug-catch" rate (predicted line within ±2 of the true line), and a per-sample record so every published number traces back to the exact example that produced it.

I built the eval harness *before* any fine-tuning happened, deliberately. A scoring rule written after you've seen which model wins is a scoring rule that's been tuned, even unconsciously, to produce that result. Locking it first was the only way to trust the comparison later.

### 3.2 Chapter 1 — a GPT from scratch

Everything under `ch1_architecture/src/` is hand-written PyTorch — tensors and autograd only. No `nn.Transformer`, no `nn.MultiheadAttention`, no `nn.LayerNorm`, no `F.scaled_dot_product_attention`, no `transformers` import anywhere in the core. I enforce that with a literal grep-based test (`test_purity.py`) that fails the build if any of those show up, because "I promise I didn't use the built-in" is not something I trust myself to get right by memory over months of edits.

What's actually in there:

- **A byte-level BPE tokenizer** I wrote from scratch (`tokenizer.py`) — train/encode/decode/save/load — trained on a ~400 KB slice of TinyShakespeare, with a much smaller 5 KB slice reserved as the smoke-test fixture.
- **The model itself** (`model/`): hand-written LayerNorm, embeddings, multi-head attention with an explicit `matmul → scale → mask → softmax → matmul` chain (not a fused kernel — I wanted every step visible), an MLP block, pre-norm transformer blocks, and a weight-tied output head.
- **A real training loop** (`train.py`): AdamW, a hand-written warmup-then-cosine learning-rate schedule, gradient clipping, Weights & Biases logging, periodic text sampling during training, and atomic checkpointing (write to a temp file, then rename, so a crash mid-write can't corrupt the checkpoint).
- **A KV-cache** (`kv_cache.py`), lazily allocated and pre-sized, wired into attention and the generation loop, with a test that proves cached and uncached decoding produce *identical* logits — not just "looks about right," bit-for-bit equivalent, because a cache that's merely fast but subtly wrong is worse than no cache.
- **Quantization** (`quantize.py`): an absmax `QuantizedLinear` layer supporting fp16, int8, and int4 (int4 packs two weights per byte), plus a benchmark script that measures tokens/sec (cached and uncached) and perplexity for every mode and writes the results to `eval/results/ch1_benchmark.json` alongside two plots.

**Two bugs from this chapter that taught me more than the parts that worked first try:**

*The causal-mask slice.* My own design notes said the causal mask slice needed "no change" once the KV-cache was added, and the literal expression I'd written down was `mask[:T, :S]`. Taken literally, that's wrong: during a cached decode step you're only feeding the model one new token at a time, so `T=1`, and `mask[:1, :S]` is *row zero* of the causal mask — which only unmasks column zero, silently blinding the model to every cached position except the very first one. The fix was to slice starting from the position of the first query in the current forward pass rather than from zero: `mask[seq_offset:seq_offset+T, :S]`, where `seq_offset` is `0` during a normal forward pass and `cache.current_len` during a cached one. Written that way from the start, the KV-cache genuinely never has to touch that line later — which was the actual intent, even though my first draft of the expression didn't achieve it. This is the kind of bug that doesn't crash — it just quietly makes the model dumber during generation, which is exactly why I insisted on the logit-identity test rather than eyeballing sample quality.

*Undecodable bytes during sampling.* The vocabulary is seeded with all 256 raw byte values so the round-trip guarantee (`decode(encode(t)) == t` for arbitrary text) holds. That means a barely-trained model at step zero can legitimately sample a byte sequence that isn't valid UTF-8 on its own — a lone continuation byte, for instance — and the very first smoke run crashed on exactly that during periodic sample-logging. The right fix wasn't in the tokenizer (which should stay a clean id-to-bytes contract); it was a narrow try/except around the decode call in the training loop's logging step, printing a placeholder for genuinely undecodable output instead of crashing a run over expected behavior from an untrained model.

### 3.3 Chapter 2 — QLoRA fine-tune for structured code review

`ch2_adaptation/` fine-tunes `Qwen2.5-Coder-1.5B-Instruct` with QLoRA (4-bit base weights, LoRA adapters) to review Java/Spring code and emit JSON matching `eval/schema.json`. The pieces:

- **`schema.py` / `prompts.py`** — the task contract and the prompt templates used consistently across the fine-tune, the base-model comparison, and the frontier baseline, so all three systems see the same instructions and only the weights differ.
- **`frontier.py` / `baseline.py`** — the frontier-API few-shot baseline, with an explicit, logged usage/cost accounting object (`Usage`) so the ≈$1 budget is a number I can point to, not an estimate.
- **`data_gen.py`** — synthetic training-data generation: inject a bug into clean Java, ask the frontier model to review it, validate the response against the schema, deduplicate against both the held-out set and anything already generated, and check remaining budget *before* every network call rather than after — because an abort that happens after the API call has already been billed defeats the entire point of a budget guard.
- **`holdout_curator.py`** — builds and freezes the 40-record evaluation set (30 hand-written synthetic-clean examples, 10 mined from real Java/Spring code) and content-hash-deduplicates it against both the training data and an earlier draft set, so nothing in the eval set can have leaked into training.
- **`lora.py` / `model.py` / `finetune.py`** — the actual QLoRA setup and training loop.
- **`evaluate.py`** — runs the shared `eval/harness.py` against the fine-tuned model, the base model, and the frontier baseline, all on the same frozen holdout, to produce one head-to-head table.

**The rule I take most seriously in this chapter: the holdout set is sacred.** No training code, no data-generation code, no prompt-tuning code is allowed to read it, and that's enforced automatically, not just documented — anything that tries to read or write `eval/holdout/` outside of an explicit evaluation context gets refused. The reasoning: the whole point of Chapter 2 is a defensible comparison, and a comparison where the training process could have seen the test set, even accidentally, isn't defensible no matter how good the resulting number looks.

I'm also upfront in the README about what this comparison actually measures: it's *distillation*, not independent discovery. A frontier model generated the synthetic training labels, so the fine-tuned model is a small specialist trained on that signal, not a system that independently reinvented code review. What the eval table honestly answers is narrower and, I think, more useful: can a 1.5B model taught by a frontier model's outputs match or beat that same frontier model's *live* few-shot performance on the one task it was taught — at a fraction of the cost, with no code leaving the network, running on CPU. Where the fine-tune loses, the table says so next to where it wins.

### 3.4 Chapter 3 — serving, monitoring, and shipping it

`ch3_operation/` takes the Chapter 2 adapter to a served, containerized, (eventually) deployed endpoint:

- **`scripts/merge_adapter.py` → `export_gguf.py` → `quantize_gguf.py`** — merge the LoRA adapter into the base weights, convert to GGUF, and quantize it for CPU inference via llama.cpp.
- **`model_backend.py` / `serve.py` / `api/main.py`** — a FastAPI app with a `POST /v1/review` endpoint that runs inference and validates the output against the schema before returning it. A model that fails to produce valid JSON returns an honest `422` — it is never silently reshaped into something that merely *looks* like a success. Every response, success or error, carries an `X-Request-Id` header, and error bodies use one consistent envelope shape across the whole API.
- **`api/errors.py`, `api/validator.py`, `api/middleware.py`** — the guardrail layer: a `400` for a malformed or empty request, `413` for an oversized payload, `422` for a schema violation, `500` for a genuine inference failure, `503` if a request arrives before the model has finished loading.
- **`api/metrics.py`** — a Prometheus-format `/metrics` endpoint tracking latency and request counts, plus drift-monitoring logic to catch the served model's output quality degrading over time.
- **`docker/`** — a CPU-only image (no CUDA anywhere) that fetches its `.gguf` file at container start rather than baking a multi-gigabyte weight file into an image layer, so the same image works against any model repo on the Hub.
- **`scripts/deploy_space.sh` / `scripts/smoke_deployed.py`** — the deploy tooling and a post-deploy smoke check for pushing the service to Hugging Face Spaces' free CPU tier.

**A concrete bug I only found by actually running the container, not by reading the Dockerfile:** the API's error handling worked correctly when exercised through the test client directly, but a `POST /v1/review` with an empty `code` field, sent through the real running container, came back as a raw `500` instead of the intended `4xx` — the app was 500'ing on its own error-formatting path, not on the request itself. It only surfaced once I actually built the image, ran the container, and hit the live endpoint end-to-end instead of trusting unit tests against an in-process app; I've since made "actually build and run the container" a required step before calling containerization done, not an optional nice-to-have.

## 4. How I tested it

A few principles I held to across all three chapters:

- **Every entrypoint has a `smoke` config that runs on CPU in seconds**, alongside a `full` config meant only for a manual GPU run. `ruff check . && black --check . && pytest -q` is the one command I run before any commit, and it has to stay green.
- **A test for every new module**, not just the ones that felt risky. As of the last full run this covered 361 passing tests across the shared eval code and all three chapters (plus a handful of tests skipped by default because they need a live GPU, a Docker daemon, or a real model download).
- **Tests exercise real code, not mocks, wherever the previous stage's output is cheap to produce.** The KV-cache tests run the actual uncached and cached forward passes and diff the logits directly, rather than asserting against a hand-computed expected value. The Docker test (opt-in, since it needs a daemon and takes minutes) actually builds the image, runs the container, and hits `/health`, `/metrics`, and the review endpoint over real HTTP.
- **A dedicated purity check for Chapter 1** — a literal grep across `ch1_architecture/src/` for banned imports and PyTorch's built-in transformer primitives, run as part of the normal test suite, so "pure PyTorch" isn't a claim I have to re-verify by memory every time I touch that code.
- **A determinism test**: the same seed run twice through the Chapter 1 smoke training loop produces an exactly equal loss curve, which is what makes every other number in this project traceable back to a specific config and seed rather than "it worked when I ran it once."

One process mistake worth being honest about: early on I marked the foundation work item "done" without mechanically re-checking every one of its acceptance criteria against the actual repo tree, and it turned out one of them — a `scripts/` directory referenced by later specs — didn't actually exist yet. Nothing downstream broke because I caught it before it mattered, but it's the reason I now treat "done" as a status that has to be earned by re-running the actual criteria, not asserted from memory of having done the work.

## 5. Problems I hit that weren't in the plan

A few of these cost real time and are worth recording honestly rather than smoothing over, because the wrong turns taught me more than the parts that went smoothly:

- **Test collection collisions.** Four different packages each had their own `test_config.py`. Without package markers in the test directories, pytest's default collector couldn't tell four same-named test modules apart and refused to run. My first fix (switching pytest's import mode) made things *worse* — it started inserting fake placeholder modules into `sys.modules` that shadowed the real installed packages, producing a more confusing error than the one I started with. A `conftest.py` manipulating `sys.path` didn't help either, because the actual problem was never path ordering. What actually worked was the simplest option I'd skipped past: rename the colliding test files to unique names.
- **A "clean commit" guard test that failed and looked like a hook bug, but wasn't.** While verifying the commit-hygiene guard, a case I expected to pass (committing a clean tree) came back refused. The guard was right; my test setup was wrong — I'd used a git command to reset the staged index that silently doesn't work in a repository with zero commits yet, so a leftover test file was still staged and the guard correctly objected to it. Worth remembering: a guardrail firing when you didn't expect it to is a reason to check your own setup before assuming the guardrail is broken.
- **A silent build-order bug in my own backlog file.** I renamed all 24 spec files to carry a numeric build-order prefix for readability, and the rename itself worked — but two things elsewhere in the repo parsed those filenames as an interface, not just as file listings, and both broke silently: a glob pattern that could no longer find any spec file by its short ID, and a status-table parser that expected the ID in a specific column and, after I added a numbering column, matched nothing at all. Neither was caught by tests, because neither had one — I only found both by actually exercising the things that read the file, not by re-reading the diff. The lesson that stuck: a file that other automation parses is an interface, and renaming it is a compatibility-breaking change even when the content inside is untouched.
- **An unexpected real result, not a bug: fp16 was *slower* than fp32 on CPU** in the Chapter 1 quantization benchmark. My first instinct was to assume a bug in the quantized kernel. It isn't — CPU inference at these sizes is memory-bandwidth-bound, not compute-bound, and fp16 arithmetic on a CPU without native fp16 support pays a conversion tax that swamps any bandwidth savings. I kept this in the results and wrote up why in `docs/quantization.md`, because reporting a counter-intuitive real result honestly is worth more than a benchmark that only shows the flattering cases.

**Code-complete, tested against smoke-scale data, waiting on a full GPU run or a deploy step I haven't pulled the trigger on yet:**
- Chapter 2's full pipeline (synthetic data generation, holdout curation, the QLoRA fine-tune, the head-to-head evaluator) — all of it runs correctly against smoke-sized data; the actual multi-hour fine-tuning run against the real dataset happens on a GPU box, by hand, and hasn't been launched yet.
- Chapter 3's GGUF export and re-evaluation — blocked on having a real fine-tuned adapter to export, which is blocked on the above.
- Chapter 3's actual deployment — the deploy script and post-deploy smoke check are written and tested, but publishing a real public URL is a deliberate manual step I haven't taken, since it also needs a real quantized model behind it.
- Chapter 1's training loop, KV-cache, and quantization benchmark — all fully implemented and tested end-to-end against a *smoke*-scale model; the meaningful, publishable numbers (a real speedup curve, a real perplexity-vs-quantization tradeoff, genuinely coherent generated text) need the full-scale run, which I've deliberately kept off this machine per the project's own compute-budget rule.

I want to be direct about why the README doesn't have filled-in numbers yet in a few places: I would rather ship an honest "pending a GPU run" placeholder than publish a number produced by an undertrained smoke-scale model under a heading that implies it's a real result. A 50-step model trained on a 5 KB corpus produces a perplexity number, technically — publishing it as "Chapter 1's headline result" would be a lie of framing even if every digit in it were accurate.

## 7. What this project actually demonstrates

Stepping back from the day-to-day log:

- I can implement a transformer's core mechanics — attention, the training loop, KV-caching, quantization — without relying on a library to hide the details from me, and I can find and fix the kind of subtle correctness bug (the mask-offset issue) that a naive implementation would ship silently.
- I can design and run a fine-tuning comparison that's actually trustworthy — a frozen, leakage-checked holdout set, a scoring contract locked before any model sees the data, and a result that reports honestly where the smaller specialist loses, not just where it wins.
- I can take a model past the "it works in a notebook" stage: schema-validated serving, structured error handling, latency and drift monitoring, a container that's actually been built and run rather than just written, and a deploy path that's ready to execute.
- I can plan before I build. Every one of the 24 work items in this project had its scope and its pass/fail criteria written down before I touched the corresponding code, and the backlog table in `specs/STATUS.md` reflects real state, not aspirational state — including the parts that are still open today.

The project isn't finished — Chapter 2's fine-tuning run and Chapter 3's public deployment are the two big remaining steps, both gated on deliberate manual actions (a GPU-box run, a "yes, publish this URL" decision) rather than on unsolved problems. Everything that can be proven without spending GPU hours or going live has been built, tested, and is green.
