# LLM Engineering: From Architecture to Edge — Build & Spec Plan

> **Status:** Draft v1 · Spec-driven development (SDD) plan for a solo build with Claude Code.
> **Scope of this document.** Everything needed to *start* the project the SDD way: the locked design decisions, the repository shape, the full Claude Code configuration (CLAUDE.md, skills, slash commands, hooks, subagents, MCP servers, plugins), the SDD workflow, and an **ordered, high-level spec backlog**. Exact technical implementation for each spec is written later, one spec at a time, against this plan.
> **Constraints carried over.** Solo developer · weekends over ~6 months · ~$25 total LLM-API budget (this project needs ≈ $1) · free GPU (Colab / Kaggle) plus a college GPU cluster · existing Claude Code + Copilot access.

## 1. Locked decisions

These were settled before writing this doc. Everything downstream assumes them.

| # | Decision | Choice |
|---|---|---|
| 1 | **Repo structure** | Single **monorepo**, three independent packages (`ch1_architecture/`, `ch2_adaptation/`, `ch3_operation/`) + shared `eval/` and `specs/` at root. One README, one architecture diagram, one portfolio link. |
| 2 | **Fine-tune task (Ch2)** | A **Java/Spring code reviewer that emits structured JSON** (`{severity, category, line, issue, suggested_fix}`). Narrow, objectively gradable, and reusable by the Career Copilot + SWE-agent projects. |
| 3 | **Data strategy** | **Synthetic training data** generated by a frontier API (≈ $1), framed honestly as **distillation into a small specialist**; the **evaluation set is independent and partly real** (mined real diffs/lint findings) so the headline comparison is not circular. |
| 4 | **Base model** | **Qwen2.5-Coder-1.5B** as default (most mature QLoRA recipes, fits a free GPU); **3B as a stretch**. Exact tag (base vs instruct) is fixed in spec C1. |
| 5 | **"Edge" target (Ch3)** | Committed: **quantized GGUF, CPU-only** (llama.cpp / Ollama) + a **free Hugging Face Spaces CPU demo**. Optional stretch: **in-browser via WebLLM/WebGPU**. |
| 6 | **Compute topology** | Hard rule: **all code must run end-to-end on a tiny CPU "smoke" config** locally / in CI; **full training/fine-tune runs are launched manually on the GPU box** (Colab/Kaggle/cluster). Claude Code never starts a full run inside a session. |
| 7 | **SDD framework** | **Native Claude Code primitives** (CLAUDE.md + custom commands + skills + subagents + hooks), with a small command set modeled on the GitHub Spec Kit flow. No external framework required. (Spec Kit can be layered later if specs must outlive sessions for an outside reader.) |

## 2. What we're building (plain language)

Three connected chapters on the theme "I understand a model from its internals all the way to a deployed edge service." They share a narrative, **not a single model**: Chapter 1 proves understanding on a toy you build by hand; Chapters 2–3 take a *real* small open model to the edge.

**Chapter 1 — Architecture.** Build a small GPT-style language model from scratch in pure PyTorch — hand-written embeddings, multi-head attention, MLP, norm, the training loop — then add a **KV-cache** and **quantization**, and produce a measured **tokens/sec speedup curve** and a **perplexity-vs-quantization tradeoff**. Goal: prove you actually understand transformers, not that you can run someone's repo.

**Chapter 2 — Adaptation.** **QLoRA fine-tune** the chosen small open model on the Java/Spring code-review task, then prove it with a **head-to-head eval table**: fine-tuned vs base vs frontier-API few-shot, on a held-out set. Goal: demonstrate the most in-demand GenAI skill — turning a generalist into a cheap, private specialist that wins on one narrow task.

**Chapter 3 — Operation.** Quantize the fine-tuned model to **GGUF**, serve it behind a **FastAPI** endpoint with **JSON-schema validation** and **latency/throughput/quality-drift monitoring**, containerize it, and deploy it to **HF Spaces + a cloud free tier**. Goal: turn "I trained a model" into "I operated one" — the production/MLOps slice.

## 3. Architecture & data flow

```
CHAPTER 1 — ARCHITECTURE  (pure PyTorch, local; toy model, throwaway weights)
  corpus → tokenizer → [embeddings → N×(attention + MLP + norm) → head]
         → custom training loop → coherent-text generations
  then:  + KV-cache  → re-benchmark tokens/sec
         + quantization (INT8 / 4-bit) → tokens/sec + perplexity tradeoff curve

CHAPTER 2 — ADAPTATION  (heavy run on GPU box; real Qwen-class model)
  task spec + JSON schema
  synthetic (buggy-code → review-JSON) pairs  ──┐
  real held-out review set (mined)  ────────────┤→ eval harness
  base model ──► QLoRA fine-tune ──► adapter ───┘
         → EVAL TABLE: fine-tuned vs base vs API few-shot (held-out set)

CHAPTER 3 — OPERATION  (CPU edge + free hosting)
  merge adapter → quantize → GGUF
         → FastAPI serve (+ JSON-schema validation, guardrails)
         → monitoring (latency p50/p99, throughput, quality/drift)
         → containerize → HF Spaces (CPU) + cloud free tier
         → [stretch] in-browser WebLLM / WebGPU
```

**Boundaries that matter:** Chapter 1 is an *independent* track (no dependency on 2/3). Chapter 3's serving skeleton can be stood up early against the *base* model as a thin end-to-end slice, then swapped to the fine-tuned model once Chapter 2 lands.

## 4. Tech stack

- **Ch1 core:** pure PyTorch (tensors + autograd only; **no** `nn.Transformer`, no `transformers` in the core), a hand-rolled or minimal BPE tokenizer, Weights & Biases for loss/perplexity.
- **Ch2:** Hugging Face `transformers` + `peft` (QLoRA) + `trl`, `bitsandbytes` (4-bit), `datasets`; ≈ $1 frontier API for synthetic data; W&B for runs.
- **Ch3:** `llama.cpp` / Ollama (GGUF, CPU), FastAPI, Pydantic (schema validation), Prometheus-style metrics, Docker; HF Spaces + cloud free tier (Railway/Render/Fly.io). Stretch: WebLLM/MLC for browser.
- **Cross-cutting:** `uv` (env/deps), `ruff` + `black` (lint/format), `pytest`, config via YAML/Hydra-style, deterministic seeds, GitHub Actions CI running the **CPU smoke configs only**.

## 6. Claude Code configuration for SDD

The setup below is deliberately lean. The guiding principle: **deterministic guardrails in hooks, repeatable workflow in commands, isolated heavy thinking in subagents, and the minimum of always-loaded context in CLAUDE.md.**

### 6.1 `CLAUDE.md` — the constitution (keep it short)

CLAUDE.md is read at the start of every session, so it costs tokens on every turn. Keep it to the non-negotiables, the map, the commands, and a pointer to specs. Recommended contents:

```md
# LLM Engineering: From Architecture to Edge

## What this repo is
Three independent packages: ch1_architecture (from-scratch GPT, pure PyTorch),
ch2_adaptation (QLoRA fine-tune of Qwen2.5-Coder-1.5B for Java code review → JSON),
ch3_operation (GGUF serve + monitor + deploy). See README.md for the diagram.

## Non-negotiables (hard rules)
1. NEVER start a full training/fine-tune run in a session. Edit + run the `smoke`
   config only (CPU, seconds). Full runs are launched manually on the GPU box.
2. ch1_architecture core uses pure PyTorch only — no `transformers`, no `nn.Transformer`.
3. The eval holdout set is sacred: never train, fit, prompt-tune, or peek at it during
   training code. Leakage = invalid headline metric.
4. Structured output is a contract: Ch2/Ch3 outputs MUST validate against eval/schema.json.
5. All randomness is seeded; configs are explicit; no magic numbers in code.
6. No secrets, weights, datasets, or .gguf files in git.

## Build & test (smoke = the default Claude should run)
- ch1: `uv run python -m ch1_architecture.train --config configs/smoke.yaml`
- ch2: `uv run python -m ch2_adaptation.finetune --config configs/smoke.yaml`
- ch3: `uv run uvicorn ch3_operation.api.main:app` then `pytest ch3_operation/tests`
- all: `ruff check . && black --check . && pytest -q`

## Workflow
Specs live in specs/. Use /specify → /clarify → /plan → /tasks → /implement.
Never implement without an accepted spec + plan. Update specs/STATUS.md at each checkpoint.

## Conventions enforced in review
Type hints; functions < ~40 lines; config-driven; W&B logging on train/eval;
tests for every new module; honest metrics (report failures, no cherry-picking).
```

### 6.2 Skills (`.claude/skills/`) — model-invoked, trigger by description

Skills load themselves when relevant and encode repeatable know-how so the agent doesn't reinvent it.

| Skill | Triggers when… | Does |
|---|---|---|
| `from-scratch-guard` | editing `ch1_architecture/src` | Reminds: pure-PyTorch only, shape-check every tensor op, overfit-a-tiny-batch before claiming correctness. |
| `qlora-recipe` | working on Ch2 fine-tune | Encodes the project's QLoRA defaults (4-bit, target modules, smoke-vs-full deltas) and the "evaluate vs base vs API few-shot" requirement. |
| `eval-table` | asked to produce/refresh results | Runs the shared harness and regenerates the comparison table + plots into `eval/` and the README in a fixed format. |
| `gguf-export` | quantizing/serving in Ch3 | The merge → convert → quantize → validate-schema checklist for GGUF; verifies the served model still passes the eval contract. |
| `spec-review` *(read-only)* | a spec was just written/edited | Audits a spec for ambiguity, missing acceptance criteria, and untestable claims; delegates the verbose audit to a subagent so it doesn't eat parent context. |

### 6.3 Custom slash commands (`.claude/commands/`) — user-invoked workflow

Modeled on the Spec Kit flow but local and minimal. Each is a markdown prompt template; exact bodies are written in Phase 0 (spec F4).

| Command | Purpose |
|---|---|
| `/specify <name>` | Create `specs/<NN-name>.md` from the template: problem, scope, acceptance criteria, explicitly out-of-scope. No implementation. |
| `/clarify` | Structured, coverage-based questioning that records answers in the spec's Clarifications section before any plan. |
| `/plan <spec>` | Turn an accepted spec into a technical plan (files, approach, smoke-config shape) — still no code. |
| `/tasks <spec>` | Decompose the plan into an ordered, independently-committable task list. |
| `/implement <spec> <task>` | Implement exactly one task against the plan; one task = one commit. |
| `/smoke <pkg>` | Run the package's smoke config and report pass/fail (the only "run" command Claude should use). |
| `/eval` | Invoke the `eval-table` skill: run the harness, regenerate the comparison table + plots. |
| `/checkpoint` | Lint + test + commit + update `specs/STATUS.md`. |

### 6.4 Hooks (`.claude/hooks/`) — deterministic, non-negotiable

Hooks are scripts the agent runs at lifecycle events; they enforce rules code review can't be trusted to catch every time.

| Hook (event) | Behavior |
|---|---|
| **GPU-budget guard** (`PreToolUse` on Bash) | **The most important hook.** Blocks any command that looks like a full/long run — large `max_steps`/`epochs`, `--config*full*`, `accelerate launch`, multi-hour jobs — unless `ALLOW_FULL_RUN=1` is explicitly set. Protects the GPU budget and prevents session hangs. |
| **Leakage guard** (`PreToolUse` on Read/Edit) | Denies training/data code from reading or writing the `eval/holdout/` path. Keeps the headline metric valid. |
| **Auto-format & smoke** (`PostToolUse` after edits) | Runs `ruff --fix` + `black` on touched files; for `src` edits, runs the relevant package smoke test and surfaces failures immediately. |
| **Commit hygiene** (`PreToolUse` on git commit) | Blocks committing weights, datasets, `.gguf`, `.env`, or anything over a size threshold. |
| **Session greeter** (`SessionStart`) | Prints the active chapter, the smoke-only rule, and the next unstarted spec from `STATUS.md`. |

### 6.5 Subagents (`.claude/agents/`) — isolated context windows, scoped tools

Subagents read work "cold" and keep heavy output out of the main thread.

| Subagent | Tool allowlist | Role |
|---|---|---|
| `spec-reviewer` | Read, Grep, Glob | Audits a spec for completeness/ambiguity without the parent's framing. |
| `code-reviewer` | Read, Grep, Glob | Reviews a diff against the §6.1 conventions; flags shape bugs, leakage, missing tests. |
| `data-curator` | Read, Write, Bash, (frontier API) | Generates + cleans the synthetic Ch2 dataset; documents provenance; dedupes against the eval set. |
| `experiment-analyst` | Read, Bash, W&B MCP | Pulls run/eval metrics, summarizes the comparison numbers, and reports just the table back. |
| `explorer` | Read, Grep, Glob, web | Research-only: reads papers/codebases/docs to extract a pattern, returns a brief. |

### 6.6 MCP servers

| Server | Why | Used in |
|---|---|---|
| **Hugging Face (official)** — `https://huggingface.co/mcp` | Search models/datasets/papers, semantic docs search (PEFT/Trainer/quantization), push to Hub, deploy/inspect Spaces, and optionally run managed training **Jobs**. | Ch2 (model/dataset discovery, push adapter), Ch3 (Spaces deploy). |
| **Weights & Biases (official)** — `wandb/wandb-mcp-server` | Query runs and Weave traces in natural language; build result reports. Backs the `experiment-analyst` subagent. | Ch1, Ch2. |
| **GitHub (official)** | Mine real PRs/diffs/review comments for the independent eval set; repo + Actions ops. | Ch2 (eval set), all (repo ops). |
| **Filesystem** *(if not native)* | Scoped file access for the agent. | All. |

Wire these in `.claude/settings.json`; tokens via env vars, never in the repo. Disable HF tools you don't need to keep the tool list tight.

### 6.7 Plugins

For a solo project, **don't adopt a heavyweight plugin**. Two lightweight moves only:
- **Package your own setup** (the commands/skills/agents/hooks above) into one **local plugin** so it's reusable across the sibling portfolio projects (Career Copilot, SWE agent).
- **Optional:** install **GitHub Spec Kit** later *only if* you want its mature `/speckit.*` command set or need specs to be readable by someone who never opens Claude Code. It coexists with the native setup.

## 7. The SDD workflow (how one spec flows)

```
/specify  →  /clarify  →  [human accepts spec]  →  /plan  →  /tasks
   →  loop: /implement <task>  →  (auto-format + smoke hook)  →  code-reviewer subagent
   →  /checkpoint (lint, test, commit, update STATUS.md)
   →  [for ML specs] launch FULL run manually on GPU box  →  /eval  →  record results
```

Rules: no code without an accepted spec **and** plan; one task = one commit; the human reviews between spec→plan and plan→implement; full ML runs happen outside the session and their numbers are pulled back via the W&B MCP / `experiment-analyst`.

## 10. Risks, cut-lines, and definition of done

**Top risks → mitigations**
- *Fine-tune doesn't beat baselines.* Task is narrow and the eval is structured-output-first, where small specialists reliably win; if quality is close, the **cost/privacy/latency** story still stands and is reported honestly.
- *Distillation-circularity objection.* Pre-empted by an **independent, partly-real eval set** (C2) and by framing Ch2 as distillation, not as "small model magically beats big model."
- *Burning GPU budget / hung sessions.* The **GPU-budget hook** (§6.4) makes a full run in-session structurally impossible.
- *Scope creep.* Chapter 1 depth, browser serving (O6), and extra quant levels are **cut-lines** — drop them before the critical path.

**Definition of done (minimum viable portfolio artifact):** F1–F4 complete; Chapter 1 through A5 with the speedup + tradeoff plots; Chapter 2 through C5 with the eval table; Chapter 3 through O5 with a live HF Spaces link; README (X1) with the diagram and results. O6 and deep Chapter-1 extensions are bonus.
